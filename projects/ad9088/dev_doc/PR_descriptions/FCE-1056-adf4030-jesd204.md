## Pull Request Description

The ADF4030 generates BSYNC and SYSREF, so it takes part in JESD204 bring-up
rather than being configured once at probe. Register it as a JESD204 device and
realign the channels that ask for it on CLK_SYNC_STAGE4, driven by an optional
init-time channel list.

That stage has no enumerator yet, so `JESD204_OP_CLK_SYNC_STAGE4` joins the op
list in `include/jesd204.h`. The FSM walks every op index in order and existing
devices leave the new slot NULL, so no other driver is affected.

Supporting fixes to existing code, each needed for the alignment to converge:

- `adf4030_poll()` takes a timeout. A TDC measurement accumulates
  2^(AVGEXP + 6) BSYNC periods, ~215 ms at AVGEXP 15 and a 9.765625 MHz BSYNC,
  which the fixed 2 s budget could not express per operation.
- `adf4030_set_tdc_measurement()` waits on MATH_BUSY as well as the
  measurement: the result is only stable once the math block has finished.
- `adf4030_set_single_ch_alignment()` writes TDC_SOURCE. It was left at its
  0x1F reset value, a channel that does not exist, so the FSM armed and never
  completed.
- `adf4030_set_alignment_iter()` touches only ALIGN_CYCLES. EN_ITER and
  EN_CYCS_RED are independent controls, and folding them in here silently undid
  whatever had just configured them.
- `adf4030_set_channel_direction()` keeps the TX path powered and lets EN_DRIVE
  alone express direction; an input channel still needs its path alive for the
  TDC to observe it.
- `ADF4030_AVGRXP` becomes `ADF4030_AVGEXP` with `GENMASK(3, 0)`. It was
  unused, misnamed and one bit too wide.

**Behaviour change worth a close look:**
`adf4030_set_alignment_threshold()` now programs the threshold only, and
enabling the iteration splits out into the new
`adf4030_set_alignment_threshold_en()`. A threshold of 0 used to disable
iteration and now programs 0. This keeps the three independent controls in
register 0x37 from undoing one another, but it does change what the IIO
attribute at `iio_adf4030.c:299` does on a write of 0 — as does the
`set_alignment_iter()` change at :295. Flagging it rather than adjusting the
IIO layer in the same commit; happy to follow up either way.

**Series** — each of these applies to `main` on its own; only the last is stacked:

1. FCE-1057-ad9088-api - ad9084/ad9088 vendor Apollo API
2. FCE-1054-cmake-firmware-blob - firmware blob embedding
3. FCE-1055-crc32 - no_os_crc32
4. **this PR** - adf4030 JESD204 support
5. FCE-1059-adf4382-phase - adf4382 phase alignment
6. FCE-112-add-ad9088-support - ad9084/ad9088 driver + VCU118 project (needs 1-5)

#### Testing

`projects/adf4030` (stm32, sdp-ck1z) builds clean in both `basic.conf` and
`iio.conf` variants.

On hardware, the part runs as the BSYNC/SYSREF provider of a JESD204C topology
on a VCU118 setup: channel alignment converges through CLK_SYNC_STAGE4, and the
converter's AXI cores report SYSREF phase locked and SYSREF captured.
